# План действий: от текущего MVP PetSpace до пилота

Документ описывает путь от состояния репозитория на сегодня до пилота по ТЗ: приложение владельца (PWA),
веб-кабинет клиники, обмен данными по согласию, интеграция с одной МИС, серверные push, деплой в РФ-облаке.

Оценки трудозатрат — индикативные (человеко-дни), сроки даны для команды 5–6 человек.
Всё, что требует внешнего решения (МИС, облако, юрист), вынесено в раздел 3 и помечено как блокер.

---

## 1. Краткий вывод

1. **Текущий репозиторий — это демо-MVP, а не основа пилота.** В нём нет ни одного пользователя:
   API открыт, любой может прочитать или удалить любого питомца. Целевой продукт придётся строить
   почти с нуля, переиспользуя UI-каркас, модель питомца и логику календаря.
2. **Порядок работ диктует безопасность.** Сначала фундамент (пользователи, роли, согласия, аудит,
   шифрование медзаписей), потом функции. Если сделать наоборот, все экраны придётся переписывать
   под модель доступа.
3. **Пятая часть объёма — это не код, а решения и интеграции:** какая МИС и есть ли у неё API,
   какое облако и GPU, какой SMS-провайдер, кто подписывает документы по 152-ФЗ.
4. **Главный технический риск — МИС.** Если у Ветменеджера/ВетАИС нет открытого API, обмен
   превращается в ручной ввод врачом или импорт файлом, и это надо принять как план Б заранее,
   а не на 13-й неделе.
5. **Главный продуктовый риск — врач.** Экономия 5–8 минут на приёме случится, только если
   карточка открывается по коду за секунды, а анамнез подтягивается сам. UX кабинета клиники
   важнее количества функций в нём.

Дополнительно найдено при аудите:

- `uploads/` в compose **не вынесен в volume** — загруженные фото терялись при пересоздании контейнера backend.
  **Исправлено:** named volume `uploads_data` + `UPLOAD_DIR=/app/uploads`, проверено пересозданием контейнера;
- `public/sw.js` был устроен наивно: кэшировал подряд все GET-ответы, включая API, и при этом нигде
  не регистрировался. **Исправлено:** кэшируется только оболочка, `/api/` и `/uploads/` не кэшируются
  никогда, регистрация включена в production-сборке; в манифест добавлены иконки (раньше массив был пуст,
  из-за чего установка на экран не предлагалась);
- таблица `subscriptions` объявлена, но не используется ни в одном эндпоинте (мёртвый код);
- в `frontend/dist` лежит собранная версия, не связанная с текущим кодом.
- **Исправлено попутно:** нет `git`, нет тестов и CI — теперь есть репозиторий с первым коммитом,
  22 теста pytest и GitHub Actions (линтер, тесты, сборка, запуск контейнеров).

Полезный вывод: MVP не выкидывается целиком. Переиспользуем каркас PWA, верстку владельца,
модель питомца, логику `overdue`, механику публичной ссылки и README по развёртыванию.

приложении. Это сохраняет главный принцип ТЗ и снимает вопрос «кто виноват в утечке».

## 4. Целевая архитектура (кратко)

```
Владелец (PWA, React)  ─┐
                        ├─→ API Gateway (Nginx/Traefik, TLS 1.3) ─→ Backend (FastAPI, /api/v1)
Кабинет клиники (web) ──┘                                                │
                                                          ┌──────────────┼───────────────┐
                                                          ▼              ▼               ▼
                                                   PostgreSQL      Redis + Celery    S3 (файлы)
                                                   (managed, PITR) (очереди, кэш)    (вложения)
                                                          │
                       МИС клиники ◄── MIS-адаптер ────────┤
                       SMS/email ◄── Провайдеры ───────────┤
                       Push (VAPID) ◄── Рассыльщик ─────────┤
                                                           ▼
                                          AI-сервис (vLLM, GPU, внутренний API) ──→ Qwen 7B+
```

### Принципы безопасности, зашитые в код

- **Пароли:** Argon2id; для клиник обязательный второй фактор (TOTP), блокировка при подборе.
- **Токены:** access 15 минут, refresh 30–60 дней с ротацией и детекцией повторного использования.
- **Шифрование:** AES-256-GCM на уровне полей медзаписей, ключи в секрет-хранилище облака,
  в записи хранится `key_id` для ротации; TLS 1.3 на входе.
- **Доступ:** роль + активный `access_grant` на конкретного питомца; проверка в одной зависимости
  FastAPI, а не в каждом эндпоинте по памяти; принцип минимального доступа.
- **Аудит:** любое чтение медзаписи клиникой пишет строку в `audit_log`.
- **Приватность по умолчанию:** публичная ссылка — длинный токен, без личных заметок владельца,
  с перевыпуском; никакие логи не содержат ПДн и тексты медзаписей.
- **Удаление по 152-ФЗ:** каскадное удаление аккаунта владельца и его данных по запросу.

## 5. Этапы работ

Оценки — человеко-дни (ч/д), индикативно.

### Этап 0. Решения, репозиторий, каркас процесса — 15 ч/д, неделя 1

- Закрыть вопросы 1–10 из раздела 3.
- `git init`, структура монорепо (`backend/`, `frontend-owner/`, `frontend-clinic/`, `ai-service/`, `infra/`).
- CI: линтеры, тесты, сборка образов на каждый коммит.
- Окружения dev/staging/prod (пока минимально), секреты вне репозитория.
- Дизайн-система (палитра, шрифты, состояния) + макеты экранов входа, Smart-ID, доступов.
- **DoD:** решения зафиксированы письменно, CI зелёный, макеты v1 приняты, доступ к тестовому стенду МИС есть или план Б утверждён.

### Этап 1. Фундамент backend: пользователи, роли, безопасность — 70 ч/д, недели 1–3

- Модель данных и миграции Alembic (таблицы выше), откат миграций.
- `/api/v1`, единый формат ошибок, пагинация, идемпотентность для записей от клиник.
- Авторизация владельца: OTP по SMS/email (TTL 5 минут, ≤5 попыток, rate limit по телефону и IP).
- Авторизация клиники: email + пароль + TOTP, приглашение сотрудника, блокировка при подборе.
- JWT access/refresh, ротация, отзыв, выход со всех устройств.
- RBAC: `owner`, `clinic_admin`, `clinic_doctor`, `clinic_registrar`, `platform_admin` + зависимость
  `require_role`; авторизация на уровне объекта (питомец принадлежит владельцу или выдан грант).
- Шифрование медзаписей, аудит-лог, согласия с версией текста.
- Redis + Celery: каркас задач (OTP, письма, напоминания).
- Тесты: доступы, шифрование, OTP-лимиты, RBAC-матрица.
- **DoD:** владелец регистрируется по коду и получает токен; чужой питомец недоступен ни по одному
  эндпоинту (проверено тестами); медзапись в БД лежит зашифрованной.

### Этап 2. Приложение владельца — 75 ч/д, недели 3–7

- Вход по коду, онбординг, экраны согласий.
- Главная: карточка питомца, ближайшее событие, вход в чат.
- Профиль питомца: все поля ТЗ, несколько питомцев, переключатель, фото (в S3).
- [x] Smart-ID: приёмы, прививки, анализы, назначения, с источником каждой записи; история изменений.
- [x] Доступы: ссылка для клиники с разделами, сроком и отзывом; список доступов; аудит открытий.
      Осталось: QR-код для этой ссылки и привязка к зарегистрированным клиникам (этап 3).
- Календарь: повторы, статусы, серверные напоминания за 3 дня и в день события (web-push).
- ИИ-чат: поток ответа, быстрые вопросы, остановка, повтор, «полезно / не полезно», загрузка фото.
- Запись в клинику: выбор клиники и времени, статус заявки.
- Настройки и удаление данных (152-ФЗ).
- PWA: регистрация service worker, офлайн-кэш Smart-ID с шифрованием на устройстве, установка на экран.
- Skeleton-загрузка, пустые и ошибочные состояния, toast, аналитика экранов, Sentry.
- **DoD:** владелец за минуту заводит питомца и выдаёт клинике доступ по QR; push-напоминание
  приходит на тестовое устройство; приложение устанавливается как PWA.

### Этап 3. Веб-кабинет клиники — 80 ч/д, недели 5–9

- Регистрация организации: название, ИНН, адрес, контакты, документы, статус проверки.
- Админка платформы: подтверждение и отклонение клиник, блокировки, метрики.
- Сотрудники: приглашение, роли, отключение.
- Поиск пациента: по коду/QR от владельца, по имени питомца и телефону (по правилу из п. 7 раздела 3).
- Карточка пациента из Smart-ID — только при активном гранте; явная плашка «доступ выдан владельцем».
- Приём: диагноз, анализы, назначения, прививки, вложения; автозаполнение анамнеза из Smart-ID.
- Заявки на запись и расписание: подтверждение без звонка, перенос, отмена.
- Напоминания пациентам о прививках и повторных приёмах.
- Аналитика: пациенты, визиты, повторные обращения, время приёма (замер для проверки цели −25–30%).
- **DoD:** врач находит пациента по коду, видит анамнез, сохраняет приём за ≤90 секунд;
  запись сразу видна владельцу; время приёма логируется.

### Этап 4. ИИ-сервис — 45 ч/д, недели 7–11

- Отдельный сервис инференса (vLLM) на GPU в РФ-облаке, внутренний API с ключом, таймауты, очередь.
- Выбор модели: сравнить на русском ветеринарном наборе 2–3 кандидата класса 7B+ (например,
  Qwen2.5-7B-Instruct, Qwen3-8B, русскоязычные дообученные варианты) по метрикам из спеки.
- Сбор контекста: профиль + сжатая история приёмов/прививок/назначений с лимитом по токенам
  (предлагаю: профиль + последние 5–10 записей + краткая сводка); контекст собирается только
  для выбранного питомца и текущего пользователя, есть тест на «не протекает чужой питомец».
- Поведенческие правила: «норма / наблюдать / обратиться к врачу», красные флаги
  (отравление, судороги, затруднённое дыхание, кровотечение) → немедленно в клинику, дисклеймер всегда.
- Оценка качества: набор 40–60 типовых вопросов с эталонами, прогон в CI, метрики, еженедельный
  разбор плохих ответов вместе с ветеринаром клиники-партнёра.
- Лимиты: rate limit на пользователя, понятное сообщение при недоступности модели.
- **DoD:** ИИ отвечает с учётом истории болезней, проходит оценку по метрикам из ТЗ, ветеринар
  подписал заключение по ответам.

### Этап 5. Интеграции — 50 ч/д, недели 9–13

- Адаптер МИС: единый интерфейс + реализация под конкретную МИС первой клиники.
- Сопоставление пациента только по коду/QR (не по угадыванию), двусторонний обмен с указанием
  источника и времени, приоритет записи врача клиники, история изменений для владельца.
- Повторные попытки, журнал ошибок, уведомление администратора клиники при сбое, ключи идемпотентности.
- **План Б, если API нет:** импорт файлом + ручной ввод врачом в кабинете (обязательно сформулировать до старта).
- Web-push (VAPID), SMS и email: шаблоны, очередь, повторы, учёт согласий и требований закона о рекламе.
- **DoD:** запись, созданная в МИС, появляется у владельца; при недоступности МИС ошибки видны в кабинете,
  данные не теряются.

### Этап 6. Деплой и эксплуатация — 35 ч/д, недели 2–14 (параллельно)

- IaC: VPC, managed PostgreSQL с PITR, Redis, S3-совместимое хранилище, GPU-инстанс, Nginx/Traefik, TLS 1.3.
- dev / staging / prod; данные пилота не используются в тестах.
- CI/CD: тесты на каждый коммит, автодеплой staging, ручное подтверждение prod, откат одной командой,
  миграции в составе релиза.
- Мониторинг: метрики API и ИИ, алерты, Sentry, централизованные логи без ПДн, health checks,
  статус-страница для клиник.
- Бэкапы: ежедневные + PITR, проверка восстановления до старта пилота.
- Секреты в защищённом хранилище, доступ к prod по ролям и с 2FA, журнал действий.
- Нагрузочный тест на 50–100 RPS (k6); целевые «300 мс при 1000 RPS» проверяем до масштабирования.
- **DoD:** восстановление из бэкапа проведено на тесте; алерт приходит в мессенджер; деплой и откат
  воспроизведены по инструкции.

### Этап 7. Юридическое и комплаенс — 12 ч/д (+ внешний юрист), недели 1–15 (параллельно)

- Уведомление РКН, политика обработки ПДн, локализация данных в РФ.
- Договор с клиникой: роли сторон, поручение на обработку, ответственность.
- Согласие владельца на передачу данных клинике и отзыв согласия — в коде, с версией текста.
- Пользовательское соглашение: ИИ-ответы справочные и не заменяют ветеринара.
- Учёт закона «О рекламе» в рассылках и push.
- **DoD:** пакет документов подписан, тексты согласий совпадают с версиями в БД.

### Этап 8. Приёмка пилота — 25 ч/д, недели 14–16

- Прогон чеклиста раздела 9, сценарий «доступ за одну минуту», тест обмена с МИС.
- Обучение клиники, инструкции для врача и регистратора, дежурство на первые две недели.
- Дашборд метрик пилота: активные пользователи, визиты, время приёма до и после, воронка экранов.
- **DoD:** пилот принят по чеклисту, метрики собираются автоматически.

**Итого:** ≈ 407 ч/д по этапам + сквозное QA (~40 ч/д) и управление/аналитика (~30 ч/д)
≈ **450–480 человеко-дней**. Это 5–6 человек на 16–18 недель. Командой из 5 человек без DevOps
и QA срок реалистично растягивается до 20–22 недель.

## 8. Риски и меры

| № | Риск | Вероятность / влияние | Мера |
| --- | --- | --- | --- |
| 1 | У МИС нет открытого API | Высокая / высокое | Выяснить на неделе 1; заранее согласовать план Б: ручной ввод + импорт файлом; не строить обмен в конце проекта |
| 2 | Врач не пользуется кабинетом, экономии времени нет | Средняя / высокое | Приём за ≤90 секунд, автозаполнение анамнеза, обучение, дежурство; мерить время с первого дня |
| 3 | GPU в РФ-облаке дорого или недоступно в нужной конфигурации | Средняя / высокое | Сравнить провайдеров, рассмотреть одну карту с автостопом, кэш ответов частых вопросов |
| 4 | Push на iPhone: web-push работает только для PWA, добавленной на экран «Домой» | Высокая / среднее | Дублировать критичные напоминания по SMS и email; в онбординге объяснять установку на экран |
| 5 | Медданные в офлайн-кэше PWA = риск утечки | Средняя / высокое | Шифровать кэш на устройстве, ограничить срок, чистить при выходе из аккаунта |
| 6 | Противоречие «поиск по телефону» и «данные принадлежат владельцу» | Высокая / среднее | Правило из п. 7 раздела 3, зафиксировать письменно |
| 7 | Метрики ИИ (F1, FP) не формализованы | Высокая / среднее | Определить задачу классификации с ветеринаром до разработки оценки |
| 8 | Оценка ИИ «на глазок», без эталонов | Средняя / среднее | Набор вопросов и прогон в CI до пилота, недельный разбор |
| 9 | Сроки: 3 клиники и 1000+ пользователей к дате пилота | Средняя / высокое | Заходить клиниками по одной, готовить онбординг, буфер 2 недели в графике |
| 10 | Нет тестов доступа → утечка медданных | Средняя / критическое | Тесты RBAC и грантов в CI как обязательное условие мержа |
| 11 | Зависимость от одного облака и одного GPU-провайдера | Низкая / высокое | IaC, бэкапы в РФ, документированный план переезда |
| 12 | SMS-расходы при входе по коду | Средняя / низкое | Лимиты на отправку, email как альтернативный канал |
